rStats.js は精度を最優先にしています。分布関数は遠い裾でも真の値との差を 1e-14 以内に保っています ([accuracy.md](accuracy.md) を参照)。その代わりに速度を犠牲にしています。この文書では、時間がどこにかかっているか、それに対して何をしてきたか、現時点での測定結果を説明します。

## 設計

### double-double 演算

double-double 数は、2 つの double の評価しない和 hi + lo で、有効桁数は約 32 桁です。部品は `src/special/dd.ts` にあります。誤差のない変換 `twoSum`、`quickTwoSum`、`twoProd` (Dekker/Knuth。JavaScript には FMA がないので Veltkamp の分割を使う) と、その上に組んだ `ddAdd`、`ddSub`、`ddMul`、`ddDiv`、`ddLog` などです。`ddExp` は `src/internal/ddexp.ts` にあります。

double の精度だけでは 1e-14 に届かないところで使っています。

- 非常に小さい確率の指数部分。Loader の鞍点法による逸脱度 `bd0` (`src/special/loader.ts` の `bd0dd`) と、指数分布、Weibull 分布、ロジスティック分布、対数正規分布での exp(−t) の引数
- 不完全ベータ関数に渡す x と 1 − x の組や n/(n + t²) のような量、および不完全ベータ関数の連分数 (`src/special/incbet.ts`)
- 非心分布のポアソン混合の和 (`src/internal/poissonMixture.ts`)
- 仮説検定での平方和と積和 (`src/internal/summary.ts`)
- Wilcoxon 順位和分布の q 二項積と、スチューデント化された範囲の積分 (`src/distributions/wilcox.ts`、`tukey.ts`。これらは誤差のない変換を手で書いている)

誤差の上界から double の精度で足りると分かる箇所では double-double の処理を省きます (下の「double の精度で足りる箇所」を参照)。それ以外では、すべての入力で double-double の経路を通ります。

### double の精度で足りる箇所

exp(−E) として計算する密度や裾の確率の相対誤差は E の絶対誤差に等しいので、各ステップについて問題になるのは、その丸め誤差の絶対的な大きさであり、そのステップに対する相対的な大きさではありません。次のステップは、この考え方に基づいて double の精度で、または少ない double-double の演算で計算します。

- **Loader の級数の残りの部分** (`src/special/loader.ts` の `bd0dd`)。x = M の近くでは、v = (x − M)/(x + M) として bd0 = d·v + 2x (v³/3 + v⁵/5 + …) です。先頭の d·v は double-double のままにし、残りは |x v³| <= 0.12、すなわち |残り| <= 1/12 のとき double の精度で合計します。その丸め誤差は高々 3 ε |残り| (捨てる v の下位部分も含む) で、E に対して ε/4 未満です。以前は残りの部分に double-double のステップが最大 16 回余分にかかっていました。
- **bd0 の遠い側の分岐での対数を 1 つに。** x log(x/M) + M − x の log(x/M) を、2 つの対数の差ではなく、double-double の商の `ddLog` 1 回で求めます (精度は同じ)。
- **線形の値の `dbeta`** は、m = ab/(a + b) として exp(−E) √(m/(2π)) / (x (1 − x)) です。exp(−E) のあとの丸めは log x の大きさによらず数回で、対数はまったく使いません。対数密度は double-double の積 x (1 − x) の `ddLog` を 1 回使います。定数 ½ log(m/(2π)) は 4 つではなく 1 つの対数です (以前の丸め誤差は約 ε (|log a| + |log b|) でした)。
- **連分数は double-double のまま**ですが、そのループは `[hi, lo]` の配列を使わないスカラーのコードとして生成し (`python3 scripts/ddgen.py cf`)、同じ演算を同じ順序で行います (割り算は結果を型付き配列に置く `sDiv` を通す)。結果はビット単位で同じで (30 万個のランダムな入力で確認)、ループは約 2 倍速くなりました。

連分数は、単純な条件で double の精度に移すことはできません。x が厳密でも、ふつうの double 演算では、double-double 版との差が a + b が 10 未満で 7e-15、a + b が 1000 前後で 1.5e-13 (a が大きく x が 1 に近いとき) に達します。この誤差は漸化式ではなく係数の丸めから来ており (係数を double にして漸化式を double-double にしても同じくらい悪い)、x が平均にどれだけ近いかを表す κ = r x / |a − r x| (r = a + b) とともに大きくなります。κ が 1e-3 未満でも (そこではもともと少ないステップで済む)、第 2 の連分数は 1e-15 ずれます。

### パラメータが大きいときの不完全ベータ関数

ab/(a + b) >= 25 で、x が平均から |τ| <= 1 の範囲にあるとき (τ = ±√(2E/m)、E は Loader の二項密度の逸脱度)、`src/special/incbetTemme.ts` は I_x(a, b) を連分数ではなく Temme の一様漸近展開で計算します。そこでは連分数の長さが √(a + b) のように伸びるためです。展開は ½ erfc(−η √(r/2)) から補正 e^(−E) e^(−D) Σ_k h_k(η) r^(−k) / √(2π r) を引いたものです。係数は表にせず実行時に生成します (変数変換の微分方程式から約 30 個のテイラー係数を求め、漸化式 h_k → g_(k+1) → h_(k+1) を回す)。そのため a と b の大きさによらず約 2 µs です。裾 (E >= 2.25) では 2 つの項がほぼ打ち消し合うので、小さいほうの裾は、項の比が約 1 + 1/E にとどまるよう組み替えた形で計算します。[0.5, 1) の引数の ½ erfc は、1 − erf ではそこで 6 倍の桁落ちがあるため、Gauss–Legendre 求積を使います。

切り替えの位置は mpmath と比べて決めました (`scripts/mpmath/largebeta.py`)。|τ| <= 1 では、展開の誤差は ab/(a + b) = 20 以上で 9e-16 以内 (連分数と同じ精度) ですが、15〜20 では 7e-15、10〜15 では 5e-14 です。速度は 10 以上で連分数を上回ります。しきい値 25 は余裕を持たせた値です。|τ| = 1 を超えると τ のテイラー級数にもっと多くの項が必要になりますが、そこでは連分数が数十ステップで収束します。

### 展開した式 (`scripts/ddgen.py`)

`[hi, lo]` の配列を返す部品は演算のたびにメモリを確保するので、ホットスポットでは時間の大半がメモリ確保と関数呼び出しに使われていました。そのため、ホットなコードはローカル変数だけで書いています。

- `dd.ts` の `ddAdd`、`ddNeg`、`ddSub`、`ddMul`、`ddMulNum`、`ddDiv`、`ddDivNum` が確保するのは結果の配列だけ
- `ddLog` と `bd0dd` の級数、および連分数のループは配列をまったく使わない

これらの展開は `scripts/ddgen.py` で生成しています。

```sh
python3 scripts/ddgen.py ops     # dd.ts の演算
python3 scripts/ddgen.py bd0dd   # loader.ts の bd0dd のうち d = x − M と級数の部分
python3 scripts/ddgen.py ddlog   # ddLog のうち表引きより後の部分
python3 scripts/ddgen.py scalar  # incbet.ts の sDiv (結果を型付き配列に置く ddDiv)
python3 scripts/ddgen.py cf      # incbet.ts の連分数の double-double のループ
```

このスクリプトは部品と同じ演算を同じ順序で出力するので、展開したコードの結果はビット単位で同じになります (ただし `bd0dd` の級数の残りの部分は、足りるところでは double の精度で合計します。上を参照)。式を変えるときは、スクリプトを編集して生成し直し、出力をその場所に貼り付けます。

### `ddLog`

`ddLog` は x = m 2^k と分解し、m を最も近い表の点 c = i/128 で割って、log m = log c + 2 atanh((m − c)/(m + c)) を 5 次の固定した Horner 多項式で計算します。log c の表 (double-double) と係数は Rmpfr を使って 400 ビットで計算しました。最大相対誤差は正規化数で 4.4e-32 です。非正規化数の入力は、先に 2^600 倍します。atanh の級数を 1e-34 まで項ごとに足すより約 2.6 倍速くなっています。`Math.log` から Newton 法で補正する方法は、`ddExp` の精度が足りないため十分な精度が出ませんでした。

### 分位点関数

連続分布の分位点関数は、共通のソルバー (`src/internal/invert.ts`) を使います。

- 各ステップで分布関数を 1 回だけ評価し、そこから線形の値と対数の値の両方を得る (`cdfBoth`)。2 回計算することはしない
- 対数密度の導関数 (`dlogPdf`、閉じた式) を使って u = log x で Halley 法のステップを取る。ステップが Newton 法のステップの 1/2 倍から 2 倍の間にあるときだけ採用する
- 初期値は、`qbeta` (a, b > 1) では Abramowitz と Stegun の 26.5.22、`qf` ではそれを F = (n/m) Y/(1 − Y) で写したもの、`qt` では Cornish–Fisher 展開 (A&S 26.7.5、n ≥ 3)、`qgamma` では xsf の逆ガンマ関数
- ソルバーは収束後にもう一度評価するのではなく、評価した点のうち残差が最小のものを返す。x での最後の仕上げは |log x| > 2 のときだけ行う

典型的な `qbeta` の呼び出しでは、現在、分布関数の評価が約 4.4 回、密度の評価が 3.9 回、反復が 3.5 回です。

離散分布の分位点関数は、分布関数を平均で約 2 回しか呼びません。遅くなるのは 1 回の評価が遅いとき (たとえば n が大きい `pbinom`) だけです。

### 精度と速度の兼ね合いを測る

`src/special/dd.ts` には内部用の切り替え (`setDoubleDouble`。公開 API ではない) があり、`ddExp` を含むすべての double-double の部品を、ふつうの double の演算に置き換えます。これで double-double によって何が得られ、何を失うかが分かります。

- `npm run bench` (`scripts/bench.mjs`) は、パッケージをビルドし、決まった一連の呼び出しを両方のモードで計測する。1 回ずつ呼び出し、5 回の実行の最小値を 1 回あたりの µs で示す。モードごとに別のプロセスで実行する。1 つのプロセスでモードを切り替えると、最初のモードでの V8 の型フィードバックが残り、2 番目のモードが最大 2 倍遅くなるため。`node scripts/bench.mjs <dir>` で別のビルドを測れる (そのビルドに切り替えがなければ double-double モードだけ)。入力はライブラリ自身の `setSeed`/`runif` で生成するので、どのビルドにも同じ入力が渡る
- `npm run precision-report` (`scripts/precision.sh`) は、`RSTATS_PRECISION=dd` と `RSTATS_PRECISION=double` でテストスイート全体を 2 回実行する。このモードではテストは失敗せず、代わりに各フィクスチャの誤差を `reports/precision/<mode>/` にまとめる。`scripts/precision-report.mjs` が両者を並べた表を `reports/precision/report.md` に書き出す (コミットはしない。約 7 分かかる)

すべてを double の精度で計算すると、次のようになります。

- d/p 関数は、現在の double-double のコードより 2〜4 倍速くなる (下の表を参照。`dbeta` は 2.0 → 0.51 µs)。double 精度モードでも配列の確保と関数呼び出しは残るので、この高速化は、double 精度で書き直したコードに対する控えめな下限である
- フィクスチャの約半分は、依然として許容誤差 1e-14 で合格する。閉じた式で書ける連続分布、`lgamma`、符号付き順位と順位和、`ptukey`、`chisqTest`、`tTest`、`wilcoxTest`、すべての乱数
- 主要な d/p 関数のほとんど (`dbeta`、`dbinom`、`dgamma`、`dt`、`pbeta`、`pbinom`、`pgamma`、`pchisq`、`pnbeta`、`pnchisq`、`pnt` など) と `qbeta`、`qf` は不合格になるが、誤差は 1e-10 以内に収まる (最大の誤差は 1e-13〜4e-12)
- 14 個は大幅に悪くなる。`beta` (3.1e-5)、`lbeta` (5.8e-7)、`pt` (6.2e-7)、`pnf` (1.0e-7)、`pf`、`dnf`、`pnbinom_mu`、離散分布の分位点 `qnbinom`、`qnbinom_mu`、`qpois`、`qbinom` (異なる整数を返すものがある)、`qt`、`qlogis`、`corTest` (r が ±1 に近いときの Pearson。最大 0.41)
- 遅くなるものもある。反復の打ち切り条件は double-double の精度を前提にしているので、double 精度では収束が悪くなる (`qnbinom` のテストは 9.3 秒ではなく 260 秒かかる)

これらの数字は「double の精度で足りる箇所」の変更より前のコードについてのものです。その後は、double 精度モードは速度の目安として役に立たなくなりました。このモードは部品の配列の確保と呼び出しを残しますが、生成した連分数のループはそれを避けるので、差が縮まりました。下の測定の M1 では、`pbeta`、`pt`、`pf`、`qbeta`、`qf` で既定のモードは double 精度モードの 1.0〜1.3 倍の時間しかかかりません (x64 の Linux マシンでは、`pbeta`、`pt`、`qbeta` は既定のモードのほうが速いほどでした)。

## 測定結果

Apple M1 (Mac mini)、Node.js 24、`tsc` によるビルド、1 回ずつの呼び出し、5 回の実行の最小値です。どの行も `npm run bench` で測りました。0.7.0 (漸近展開と double-double の処理の削減より前) と比べて、既定のモードは次の倍率で速くなりました: `pbeta` 1.6、`dbeta` 2.0、`pt` 1.7、`pgamma` 1.2、`pnbinom` 1.2、`dbinom` 2.1、`pbinom` 5.2 (size が 1e4 まで。多くは展開が使われる範囲)、`dgamma` 1.4、`dt` 1.8、`pf` 1.7、`pchisq` 1.3、`qbeta` 1.8 (典型) と 1.5 (裾)、`qgamma` 1.3、`qchisq` 1.4、`qt` 1.4 と 1.3、`qf` 1.7、`tTest` 1.2。「典型」の入力は、形状パラメータが 0.5〜50 の対数一様、p が 0〜1 の一様です。「裾」の入力は、形状パラメータが 0.1〜1e4、p が 1e-5〜1e-300 です。

**R・SciPy との比較。** 同じ入力での `qbeta` は、R 4.5.2 (arm64、ベクトル化した 1 回の呼び出し) で 1 個あたり典型の入力で約 1 µs、裾の入力で 2.9 µs です。SciPy 1.13 の `betaincinv` は 1.7 µs と 4.3 µs です。したがって rStats.js は、典型の入力で R より約 17 倍遅いことになります。R の `pbeta` と `dbeta` は約 0.2 µs と 0.1 µs です。答えは一致しています (典型の入力で、rStats.js と R の相対差の中央値は 1.5e-16、最大は 1.0e-14)。この差は double-double 演算の代償であり、結果が違うからではありません。

**大きなパラメータ。** 不完全ベータ関数の連分数は、中心付近ではパラメータの平方根にほぼ比例する回数の反復を必要とします。そのため 0.7.0 では、`pbeta(0.5, a, a)` が a = 10 で 4.4 µs、a = 1000 で 21.9 µs、a = 1e5 で 98.9 µs、a = 1e6 で 221 µs、`pbinom(n/2, n, 0.5)` が n = 1e3、1e4、1e5、1e6 で 18.4、39.7、79.7、169 µs かかっていました。展開 (ab/(a + b) >= 25) により、これらの呼び出しは定数時間になり、a = 1000、n = 1000 以上で 0.9〜1.1 µs です (17〜245 倍速い。a = 10 はしきい値より下なので、速くなった連分数の分だけで 4.4 → 2.3 µs)。自由度が大きい `pt` と `pf` は対象外です (一方のパラメータが 1/2 または小さい)。df = 1e6 の `pt` は 5.4 µs です (0.7.0 では 10.5 µs)。

### 線形代数

標準正規分布の値を並べた行列を使います (`chol`: crossprod + nI、対称 `eigen`: (A + Aᵀ)/2)。R 4.5.2 (arm64) は 4 スレッドの OpenBLAS 0.3.26 を使います。R の時間は、20 回の平均を 5 回測ったうちの最小値です。

| 演算 | n = 100: rStats.js | R | n = 300: rStats.js | R |
|---|---|---|---|---|
| `qr` | 1.0 ms | 0.30 ms | 21.6 ms | 4.9 ms |
| `solve` (右辺 1 本) | 0.6 ms | 0.10 ms | 11.3 ms | 1.0 ms |
| `chol` | 0.2 ms | < 0.05 ms | 5.6 ms | 0.20 ms |
| `svd` | 7.1 ms | 1.2 ms | 162 ms | 15.0 ms |
| `eigen` (対称) | 4.7 ms | 0.90 ms | 97 ms | 7.4 ms |
| `eigen` (一般) | 16.5 ms | 3.5 ms | 371 ms | 32.9 ms |

rStats.js は R より 3〜28 倍遅くなっています。R はブロック化した LAPACK と、SIMD と FMA を使う最適化されたマルチスレッドの BLAS を使いますが、rStats.js はブロック化していない素直なループを使っているためです。統計でよくある大きさの行列 (列数が数十まで) なら、1 回の呼び出しは 1 ms から数十 ms です。

サブパスの行は、その分野だけをバンドルした大きさです。CDN 向けの分野ごとのファイル (`dist/<area>.js`) は分野の間でコードを `dist/chunks/` で共有するため、そこから 1 分野を読み込むと転送量はこれより多くなります。chunk を含めて gzip で 18 KB (`numerics`) から 91 KB (`tests`) です。

不完全ベータ関数の一様漸近展開は、`pbeta` を使うもの (`qbeta`、`pt`、`tTest` など) に gzip で 1.3 KB、連分数の配列を確保しないループは 2.6 KB を加えます (割り算も含めてすべての double-double 演算を書き出すと、さらに 1.3 KB 大きくなり、ループはさらに約 1.3 倍速くなるだけでした)。

`pt` が大きいのは、非心 t の経路 (`src/distributions/nt.ts`) と double-double の部品が一緒に入るためです。中心分布だけの関数を分ければ小さくなります。

## 採用しなかった方法

- **WebAssembly。** 同じ `ddLog` を C から Wasm にコンパイルしたものは、JavaScript 版より 1.2 倍速く、relaxed-SIMD の融合積和を使うと 1.6 倍速くなりました。ただし、融合されるかどうかはエンジン次第です (融合されないと、誤差項が黙って 0 になります)。また、Wasm には非同期の初期化が必要で、関数ごとの tree-shaking ができず、検証すべきコードの経路が 2 つになります。そのため、重い行列計算や反復計算を置き換える候補として残すにとどめています。採用する場合は同じ API の裏に置き、同じフィクスチャでテストします。
- **double 精度の連分数**。パラメータが中くらいの場合に限っても、係数の丸めのために誤差が a + b が 10 未満で 7e-15、1000 前後で 1.5e-13 に達します (「double の精度で足りる箇所」を参照)。
- **1 <= n <= 15 でより正確な `stirlerr`** (7 以上は 12 項の Stirling 級数、それより下のステップは (m + ½) log1p(1/m) − 1 の桁落ちを避けて t = 1/(2m + 1) で t²/3 + t⁴/5 + … と書く)。絶対誤差は 8e-16 から 1.8e-16 に下がりますが、R 自身が 1.0e-14 ずれている R のフィクスチャの 2 ケース (`choose(4.3, 31)` と `dnbinom(7, 0.01, mu = 1e-10)`) が R に対する許容誤差のわずかに外に出ます。これらにはまだ参照値がありません。速度もほとんど変わりません。参照値を計算できるようになるまで保留しています。
- **パラメータだけで決まる項のキャッシュ** (`lbeta`、`lgamma`、`stirlerr`)。これらが占める時間は 1〜6% で、メモ化しても測定できるほどの差はありませんでした。
